has two transport attempts; these do not reset the DB lease or bypass dispatch fencing.

## Authentication and permission findings

- Ingress uses dedicated HS256 JWT credential `iNTfFNFDdmznDt0r`. The permanent signing key
  is stored in Vault and encrypted n8n credentials, not in SQL source or queue headers.
- Tickets expire after 60 seconds. They only wake the queue; no caller-selected lead, result,
  URL, message or business action is accepted. A replay can cause an empty/deduplicated wake-up,
  not a second result. Queue events are not single-use authentication tokens.
- Ingress saves neither success/error payloads nor manual/progress data; the child receives only
  `{source: database_event}` and retains operational queue IDs/receipts.
- Initial pg_net ACL hardening was a VERIFIED NO-OP: extension objects are owned by
  `supabase_admin`, not the migration role. `has_table_privilege` still showed broad transport
  grants. Do not claim these were removed. JWT tickets avoid storing a reusable signing secret
  in that transport. Vault decrypted secrets are denied to anon/authenticated.
- New private config/dispatch tables deny all client access and have RLS enabled with no
  client policies intentionally. The write-only provisioning RPC is service-only, checks the
  JWT role and accepts neither arbitrary URL nor a secret-read operation.
- Supabase security advisor reports the two intentional deny-all RLS tables as INFO, plus
  existing broad authenticated SECURITY DEFINER and leaked-password-protection warnings.
  This release is not a claim that every historical project security finding is resolved.
- Intermediate unused Header Auth credential `BnoY1T18zPA9fbD7` could not be deleted:
  the n8n API returned `DELETE method not allowed`. It is no longer referenced by the ingress.
  Do not retry deletion blindly or report it removed.
